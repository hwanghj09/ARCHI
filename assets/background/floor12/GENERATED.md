# 12층 배경 그림과 실제 적용 규격

- 2026-09-24 최초 제작: `scripts/render-floor12-art.mjs`가 CSS로 그린 벽·문·표지판 디자인을 Chromium으로 그대로
  렌더링해 PNG로 굳혔다(image_gen 아님). 이 스크립트는 지금도 저장소에 남아 있지만 더 이상 실제 게임 그림의
  소스가 아니다 — 아래 손그림 교체로 대체됐다.
- 2026-09-24 손그림 교체: `PROMPT.md`의 7장 프롬프트로 image_gen 픽셀아트를 생성해 `art-corridor-*.png`(4장)
  ·`art-interior-*.png`(3장)로 저장한 뒤, `scripts/compose-floor12-pixelart.ps1`로 `corridor.png`/`dev.png`
  /`lab.png`/`lounge.png`를 다시 만들었다. 디자인(색·모양)은 이제 이 7장의 image_gen 결과에만 있고,
  `index.html`에는 12층 전용 테마·벽·문 CSS가 없다. **`corridor.png`는 아래 "복도 재작성"으로 대체됐다** —
  `dev.png`/`lab.png`/`lounge.png`는 이 방식 그대로 유효하다.

## 문 테두리가 판정 박스를 벗어나던 문제 수정 (2026-09-25)

"복도 한 장 워프, 2차 시도"로 만든 `corridor.png`에서 문 4개(개발실·성능평가실·화장실·휴게실) 모두 **그려진
문(테두리 포함)이 실제 판정 박스(`doorX`~`doorX+doorWidth`)보다 15~30px씩 넓게 삐져나와** 있었다. 앵커를 문
좌우 "leaf(안쪽 유리/패널)" 기준으로 재서 그런데, 실제로는 그 바깥 테두리(frame)까지 포함해서 재야 했다.

**전체를 다시 워프하지 않고, 문 4개 영역만 국소적으로 수정**했다(`assets/background/floor12`에는 별도 스크립트로
안 남기고 1회성 스크립트로 직접 처리):
1. 각 문의 실제 그려진 프레임 바깥쪽 끝(outer edge)을 눈으로 재측정.
2. 그 영역만 잘라서 목표 박스 폭에 맞게 가로로 축소.
3. 문이 좁아지며 비는 좌우 가장자리는, 문 바로 바깥의 원본 벽 텍스처를 한 번에(반복 타일링 없이) 복사해서 채움
   — 처음에 20px 단위로 반복 타일링했더니 개발실 문 오른쪽에서 빨간 표시등이 복제되어 보이는 이음새가
   생겨서, 필요한 폭만큼 한 번에 샘플링하는 방식으로 다시 했다.
4. 문 바깥 영역, 엘리베이터, 전체 캔버스 크기(5000×720) 등 나머지는 전혀 건드리지 않았다.

측정값(현재 그림 기준, outer frame → target box):
- 개발실: 1000..1195 → 1030..1170
- 성능평가실: 3270..3465 → 3290..3450
- 화장실: 3595..3785 → 3612..3757
- 휴게실: 4685..4825 → 4700..4810

다음에 복도를 통째로 다시 만들 때는(`compose-floor12-corridor.ps1`), 앵커를 문의 **바깥쪽 테두리**로 재야
이 문제가 재발하지 않는다.

## 복도 한 장 워프, 2차 시도 (2026-09-25, 현재 방식)

바로 아래 "4구역 분할 생성"을 시도한 뒤, 사용자가 훨씬 큰 해상도(7831×1064)로 다시 그린 복도 한 장을 줬다.
이번엔 문 배율 차이가 구간마다 0.3~1.2배 정도로 훨씬 고르고(예전 5.4배 같은 극단값 없음), **바닥선도 처음부터
끝까지 y=800으로 일정**했다(4구역 방식에서 겪었던 "문마다 다른 두께의 턱" 문제 없음). 그래서 다시
`scripts/compose-floor12-corridor.ps1`(한 장 워프)로 돌아갔고, 4구역 스크립트보다 이음매가 없어 더 깨끗하다.
4구역 방식(`compose-floor12-corridor-zones.ps1`)은 소스가 이번처럼 잘 나오지 않을 때 대안으로 남겨둔다.

- **바닥선 측정 교훈**: 문짝이 실제로 끝나는 y(여기서는 800)를 눈으로 확인해서 쓴다. 밝기가 검게 뚝 떨어지는
  지점을 찾는 자동 스캔은 문 아래 장식용 턱의 바닥을 잡아서 최대 68px까지 틀렸던 적이 있다(자세한 내용은
  `compose-floor12-corridor.ps1`의 주석 참고).
- 앵커: 개발실 문, 엘리베이터 3대, 비상계단, 성능평가실 문, 화장실 문, 휴게실 문 — 전부 `player.js`의
  `BUILDING_CORE`/`FLOOR12_LAYOUT` 좌표 그대로. 이번엔 화장실~휴게실 사이에도 실제 그림 내용(민무늬 벽 500px)이
  충분히 있어서 필러 패치가 필요 없었다(`$UseFiller = $false`).
- 다시 만들 때:
  ```
  powershell -File scripts/compose-floor12-corridor.ps1 -SourcePath <새 그림 경로>
  ```

## 복도 4구역 분할 생성 (2026-09-25, 대안 — 소스가 위 방식으로 깔끔하게 안 나올 때)

"복도 재작성"(바로 아래 절)의 방식 — 복도 전체를 6~7:1 비율의 그림 한 장으로 받아서 구간마다 다른 배율로
늘리는 워프 — 는 문 위치는 정확히 맞았지만, 구간별 배율 차이가 너무 크면(한 번은 5.4배까지) 그 부분이
흐릿하게 뭉개지는 문제가 있었다. 17층의 확장부(`service-corridor.png`)가 "필요한 만큼만 적당한 비율로
새로 생성"했던 것처럼, **복도를 4구역으로 나눠 각각 따로 생성**하는 방식으로 바꿨다.

- 프롬프트: `PROMPT.md`의 "구역 A/B/C/D" 4개. 각 구역은 실제 필요한 폭에 가까운 비율(1:1~2.5:1)로 요청해서,
  6~7:1짜리 복도 한 장보다 문 간격이 훨씬 안정적으로 나온다.
- 합성: `scripts/compose-floor12-corridor-zones.ps1`이 4장을 받아 5000×720 캔버스에 붙인다.
  - **구역 A(개발실)·B(엘리베이터+비상계단)**: 그림 자체 비율이 목표 구간 비율과 이미 거의 같아서, 그림
    폭을 구간 폭에 맞추는 **단순 확대 하나**(왜곡 없음)로 충분하다. 바닥선만 y=570에 맞춘다.
  - **구역 C(성능평가실+화장실)**: 그림 안에서 두 문 사이 간격이 목표 간격과 살짝 달라서, 5개 앵커로 아주
    작은 워프(0.4~1.13배, "복도 재작성"의 5.4배 같은 극단값 없음)를 한 번 더 한다.
  - **구역 D(휴게실)**: 요청한 비율(0.97:1)보다 훨씬 넓게(1.39:1) 나와서, 구간 폭에 맞추면 위쪽에 빈
    공간이 생긴다. 대신 **바닥 높이(720)에 맞춰 확대**하고 문 위치로 좌우 배치를 정한다. 그 결과 그림이
    구역 C의 끝자락까지 넘어오는데, 구역 C의 마지막 앵커를 그 지점에서 끊어서 겹침·빈틈 없이 이어진다.
- 남는 것: 이 방식은 빈 벽을 다른 자리에서 잘라와 채우는 "필러 패치"가 필요 없다 — 구역들이 정확히 맞닿는
  지점에서 끝나도록 앵커/좌표를 잡기 때문이다.
- **바닥선 측정 시 주의**: 처음 만들 때 밝기 변화(밝은 스파이크나 검은색으로 뚝 떨어지는 지점)로 바닥선을
  찾았다가, 구역 B/C/D에서 문마다 20~70px씩 붕 떠 보이는 문제가 생겼다. 원인은 이 그림들이 문 바로 아래에
  30~100px 두께의 장식용 턱(curb)을 그려서, "완전히 검게 떨어지는 지점"이 턱의 **바닥**이지 문이 실제로
  끝나는 지점이 아니었기 때문이다. **반드시 문짝이 끝나는(닫히는) y 픽셀**을 눈으로 확인해서 `floorSrc`로
  써야 한다 — 그 아래 턱이 얼마나 두껍든 상관없이, 문 바닥 = 충돌 바닥선이다.
- 다시 만들 때: 새 4장을 받으면 각 그림에서 문짝이 끝나는 y(턱 두께 무시!)와 문 좌우 픽셀을 눈으로 재서
  `compose-floor12-corridor-zones.ps1`의 값(`$floorSrcA`/`$floorSrcB`/`$floorSrcC`/`$floorSrcD`, `$anchorsC`,
  `$doorLeftSrcD`)을 갱신한 뒤 실행한다.
  ```
  powershell -File scripts/compose-floor12-corridor-zones.ps1 -ZoneA <A.png> -ZoneB <B.png> -ZoneC <C.png> -ZoneD <D.png>
  ```

## 복도 재작성 (2026-09-25, 폐기됨 — 위 4구역 분할로 대체)

17층은 image_gen 결과(2172px 폭)를 **가로세로 동일 배율로 통째로 확대**해서 만들었고, 그 확대 결과에 맞춰
`BUILDING_CORE`의 엘리베이터·비상계단 좌표를 나중에 정했다(그림이 좌표를 만든 순서). 12층은 반대다 — 16층·17층이
이미 그 좌표(`BUILDING_CORE`)를 쓰고 있어서, 12층 새 그림은 **이미 고정된 좌표에 맞춰야** 한다. 통짜 확대 하나로는
문 4개(개발실·성능평가실·화장실·휴게실)와 엘리베이터 3대 간격을 동시에 맞출 수 없어서(원본 이미지 안에서 이 간격들이
서로 다른 비율로 나와 있음), **구간별로 다른 배율을 쓰는 워프**가 필요하다.

- 도구: 사용자가 직접 ChatGPT 등에서 생성한 복도 전체 1장(가로로 넓은 이미지, 세로 방향 격자로 문 위치를 육안 측정).
- 방법: `scripts/compose-floor12-corridor.ps1`이 (원본 x, 목표 x) 앵커 목록을 기준으로 앵커 구간마다 독립적으로
  가로 배율을 적용해 5000×720 캔버스에 붙인다. 세로 배율은 전체가 동일(바닥선이 화면 전체에서 완전히 수평이어야
  하는 충돌 판정 요구사항 때문)하고, 가로만 구간마다 다르게 늘어난다.
- 앵커는 대부분 **문 좌우 픽셀**이다 — `player.js`의 `BUILDING_CORE`(엘리베이터 x=1818/2148/2444, 비상계단
  x=2906)와 `FLOOR12_LAYOUT`(개발실 doorX=1030 폭140, 성능평가실 doorX=3290 폭160, 화장실 doorX=3612 폭145,
  휴게실 doorX=4700 폭110)에서 그대로 가져온다. 엘리베이터·비상계단은 `assets/objects/floor17/`의 DOM
  오버레이가 항상 그 위를 완전히 덮으므로 그 부분 그림 자체의 정렬은 대충 맞아도 되고, **방 문·화장실 문만
  정확해야** 한다.
- 세로 정렬: 원본 위쪽에 항상 비는 검은 여백이 있어(이미지 생성 도구가 두는 "밤하늘" 패딩), 그대로 확대하면
  천장이 화면 위 20%를 차지하는 빈 띠가 되어 "사진 높이가 어색"해진다. `$CropTop`(천장 디테일이 실제로 시작하는
  행)을 먼저 잘라내고, 그 지점부터 바닥선까지만 배율을 계산한다.
- 빈 벽 채우기: 화장실 문 오른쪽 끝~휴게실 시작 사이(목표 x=3757..4300, 543px)는 원본에 그만한 여백이 거의 없어서,
  다른 자리의 **완전히 민무늬인 벽 조각**을 찾아 그 폭만큼 반복해서 채운다(유리창·문·표지판이 섞인 조각을 쓰면
  반복 패턴이 이상하게 보임 — 실제로 한 번 실패했었다). 이 구간은 배경만으로는 밋밋해 보이므로
  `FLOOR12_LAYOUT.props`에 소품(냉온수기·화분 등)을 몇 개 더 놓아 크기 비교 기준을 만든다.
- 다시 만들 때: 새 복도 그림을 받으면 그림 위에 100px 격자를 씌워(또는 아무 이미지 편집기로 확대해서) 각 문의
  좌우 픽셀 x를 읽고 `scripts/compose-floor12-corridor.ps1`의 `$Anchors`와 `$CropTop`/`$FloorSrc`를 갱신한 뒤:
  ```
  powershell -File scripts/compose-floor12-corridor.ps1 -SourcePath <새 그림 경로>
  ```
  기본 출력 경로는 `assets/background/floor12/corridor.png`다.
- 네 파일 모두 **월드와 1:1** 불투명 PNG: 가로 = 장면 폭, 세로 720, 바닥선 y=570. 그래서 정렬 계산이 필요 없다
  (`top: 0`, `height: 720`, 가로 = `config.width`).
- 방 내부 3장(`dev.png`/`lab.png`/`lounge.png`)의 합성 방법(`compose-floor12-pixelart.ps1`, 2026-09-24 기준,
  지금도 유효): image_gen 결과 7장은 모두 1536×1024 캔버스.
  - **실내 3장**(`art-interior-*.png`)은 문 중심 위치 비율이 실제 exitDoorX 비율과 거의 일치해서(예:
    art-interior-dev.png 문 중심 ≈ 50%, 실제 dev 방 exitDoorX 문 중심 ≈ 51%), 타일링 없이 방 폭
    (3600/1808/2560)×720으로 가로·세로를 따로 늘려 그대로 dev/lab/lounge.png로 저장한다.
  - **복도 4장**(`art-corridor-*.png`)은 이 방식이 실패했다 — 그림 속 문 크기가 12층 CSS 조각(참고 스케치)의
    비율을 그대로 따르지 않아서, 슬롯 폭에 맞춰 그대로 늘리면 문 크기·바닥선 높이가 조각마다 달라져 보였다
    (예: lab↔restroom 이어지는 부분에서 바닥선이 약 80px 어긋남). 그래서 복도 4장은 **1536×1024 그림에서
    문 좌우 픽셀(눈으로 100px 격자를 씌워 측정)을 찾아, 그 문 폭이 코드의 doorWidth와 정확히 같아지는 하나의
    배율(가로·세로 동일, 왜곡 없음)로 통째로 늘린 뒤**, 문이 코드의 doorX·바닥선(y=570)에 정확히 오도록
    옮겨서 방 슬롯에 클리핑해 붙인다. 슬롯보다 넓게 늘어난 부분은 잘리고, 슬롯 위쪽에 그림이 못 미치는
    빈틈은 그림 맨 위 줄 색을 채운다(스크립트의 `Get-EdgeColor`).

## 연결

- `player.js`: `floor12Art(name)` → `{ src, height: 720, top: 0, flat: true }`을 `FLOOR12_LAYOUT`과 `FLOOR12_ROOMS`의
  `backgroundImage`로 쓴다. `flat: true`이면 `buildDynamicScene`이 `#dynamic-scene[data-art="flat"]`을 붙인다.
- `index.html`의 `data-art="flat"` 규칙: CSS 바닥·실내 벽을 숨기고, 문은 테두리/배경만 투명하게 해 접근 외곽선
  (`.near`)만 보인다. 방 표지판(`.floor-room-sign`)과 층 번호판(`.floor-number-sign`)은 **DOM 글자로 남겨서 보인다** —
  손그림에는 글자가 없기 때문이다(위 PROMPT.md 공통 프롬프트의 "No text, no letters" 규칙). 소품은 16층식
  `data-art="true"`처럼 어둡게 하지 않는다: 이미 그림 자체가 정전 톤을 담고 있어서 추가로 어둡히면 안 된다.
- 출구 x는 `exitDoorX`가 계산한 값과 같다(구도 확인 표는 아래 참고). 그래서 `exitX`는 적지 않는다.

## 문 주변 재합성(17층 방식, 2026-09-26)

`dev.png`의 문 주변은 원래 "문을 목표 폭(140)으로 줄이고, 줄여서 빈 26~27px 틈을 다른 자리에서 샘플링한
벽 조각으로 채우는" 방식으로 만들었는데, 채우기 샘플을 여러 번 바꿔도 계속 "문 옆에 문 흔적", "배지리더
중복", "문 중간에 다른 사진이 덮인 것 같다" 같은 티가 났다. 17층 `office-interior-aligned.png`(`OFFICE-PROMPT.md`
참고)처럼 **원본 픽셀을 자연스러운 경계에서 자르고 순서만 바꾸며, 아무것도 새로 만들어 채우지 않는** 방식으로
다시 만들었더니 이 문제가 없어졌다:

1. 새 실내 원본(2804×561, 문 좌우 프레임 바깥쪽 기준 native x=1358..1500)을 바닥선 배율(570/420=1.357)로만
   가로·세로 동일하게 확대한다(3805×761 → 720으로 크롭). 이 배율 하나만 적용하고 그 외에는 리샘플하지 않는다.
2. 확대된 좌표에서 문틀 바깥쪽 가장자리를 다시 실측하면 x=1796..2019(폭 223, 천장 파이프·비상등·표지판까지
   포함하는 세로 기둥 전체). 이 통짜 조각 **하나만** 목표 폭 140으로 줄인다(가로만 0.628배, 세로는 그대로) —
   문을 반으로 갈라 따로 옮기지 않으므로 문 한가운데 이음선이 생기지 않는다.
3. 문 오른쪽의 배지리더(카드 인식기)는 문틀 바로 옆(x=2019 이후)에 원본 그대로 남아 있어 별도로 자르거나
   옮길 필요가 없다 — 문 조각을 줄인 뒤 그 오른쪽에 원본을 그대로 이어 붙이면 배지리더가 문 옆 원래
   비율 그대로, 딱 한 번만 나온다.
4. 최종 3600px 폭 = **왼쪽 원본 그대로 1775px(문 바로 왼쪽 경계까지) + 줄인 문 140px + 오른쪽 원본 그대로
   1685px**. 원본이 필요한 것보다 넓어서(3805px) 타일링(반복)이 전혀 필요 없었다 — 양 끝에서 남는 부분만
   그냥 잘라냈다. 채워 넣은 픽셀은 한 군데도 없다: 문 조각(리사이즈 1곳) 말고는 전부 원본 그대로다.
5. Playwright로 실제 페이지에서 `f12-dev`의 `.room-door`(badge)를 찍어 `left:1775px, width:140px, top:280px,
   height:290px`를 확인해 그림과 정확히 일치함을 검증했다.
6. **바닥선 배율 재확인(중요)**: 처음에는 원본 바닥선이 native y=420인 줄 알고 배율(570/420=1.357)을 잡았는데,
   실제로 픽셀을 다시 스캔해보니 밝은 바닥선 피크는 y=424였다(4px 차이). 이 4px가 배율(1.357)에 곱해져 완성된
   그림에서는 바닥선이 y≈575에 그려졌다 — 코드의 `floorY=570`보다 5px 아래. 소품(책상 등)은 `floorY - (height-8)*scale`
   공식으로 y=570에 발이 닿게 배치되므로, 그림 바닥선이 570보다 아래 있으면 책상이 그림 속 바닥선보다 위에 떠
   보인다("책상이 전부 공중에 떠 있다" 버그, 2026-09-26). **원본에서 바닥선 배율을 잴 때는 반드시 밝은 줄의
   피크 행(row-by-row 밝기 합 최댓값)을 직접 스캔해서 찾을 것 — 눈대중으로 어림잡은 행 번호는 몇 px씩 틀리기
   쉽고, 이 배율 하나가 이미지 전체 가로세로 크기에 곱해지므로 작은 오차도 문 위치·바닥선 위치를 함께 어긋나게
   만든다.** 고친 뒤 배율 570/424=1.3443으로 다시 만들었고, 완성된 `dev.png`에서 x=200/900/1500/2500/3300 등
   여러 지점을 다시 스캔해 바닥선 피크가 전부 정확히 y=570에 오는 것을 확인했다.

**다시 이 문제가 나면**: "빈 틈을 다른 자리 샘플로 채운다"는 접근 자체를 피하고, 위 순서대로 (a) 문(그리고
같이 움직여야 하는 표지판·조명까지 포함한 세로 기둥) 하나를 통짜로 리사이즈, (b) 그 좌우는 원본 그대로 크롭,
(c) 필요하면 양 끝만 잘라 폭을 맞추는 방식을 먼저 시도한다.

## dev.png 배경 자체를 새 복도 그림 기준으로 교체(2026-09-26, 2차)

사용자가 새 복도 원본(7831×1064, `corridor.png`에 쓴 것과 같은 종류의 그림, 자체는 corridor.png 교체용이 아니라
"개발실 안쪽도 이 사진처럼"이라는 요청으로 줌)을 줬다. 이 그림 속 ARCHI 개발실 유리벽 너머로 보이는 책상 줄
모습을 dev.png의 새 배경으로 썼다(이전 `art-interior-dev.png`/이미지61 기반 데스크 디자인을 완전히 대체).

1. 바닥선: 이 종류의 복도 원본은 이전 것과 같은 비율이라 바닥선이 native y≈799(=`corridor.png`가 쓰는
   FLOOR_SRC=800과 거의 같음)에 있다 — 픽셀 밝기를 스캔해서 확인(어림잡지 않음). 배율 = 570/799.
2. 문(badge)은 이 그림에서 native x=1290..1531(바깥 프레임 기준, 스캔으로 확인), 배지리더는 그 바로
   오른쪽 x=1531..1600. 문은 위 절과 같은 방식으로 통짜 리사이즈해 폭 140으로 줄여 x=1775에 붙였다.
3. **이 복도 그림에서 ARCHI 개발실 유리벽 구간 자체가 3600px보다 훨씬 좁다**(문 왼쪽 실사용 가능 구간은
   겨우 native 0..1290, 문 오른쪽은 1600..2450 — 그 다음은 기둥과 엘리베이터 벽으로 바로 이어진다). 그래서
   이번에는 복도.png 만들 때처럼 **반복 타일링이 실제로 필요했다**: 문 왼쪽 끝(비상구 표지판+기둥+창 4개,
   native 0..1290)은 그대로 한 번만 쓰고, 그 뒤 모자라는 폭과 문 오른쪽 전체는 **책상 하나+창 하나가 담긴
   깨끗한 조각 한 개**(native 1600..2150, 책장·화분 같은 고유 소품이 섞이지 않은 구간만 골랐다 — 바로
   옆 1600..2450에는 책장+화분이 있어서 반복하면 여러 번 나오므로 제외했다)를 필요한 폭만큼 이어 붙였다.
4. 이어붙인 자리(왼쪽 캡↔반복 조각, 반복 조각↔반복 조각, 문↔배지리더)를 2배 확대로 하나씩 확인해 어색한
   이중선이나 잘린 소품이 없는지 봤다. 반복 조각끼리의 이음매는 같은 그림이 그대로 반복되는 것이라 사실상
   안 보이고, 왼쪽 캡과 반복 조각 사이만 살짝 다른 소품 배치가 보이는데 눈에 띄는 수준은 아니었다.
5. 완성 후 x=50/500/1000/1700/2000/2500/3000/3500 등 여러 지점에서 바닥선 피크 행을 다시 스캔해 전부
   정확히 y=570임을 확인했다.

**다시 만들 때 체크리스트**: (1) 새 원본의 바닥선 native 행을 스캔으로 재라, 어림잡지 마라. (2) 문·배지리더
바깥쪽 프레임 경계를 스캔/격자로 재서 통짜 리사이즈 폭을 정해라. (3) 문 좌우로 반복 없이 쓸 수 있는 원본
구간이 얼마나 되는지 먼저 확인하고(고유 소품이 섞인 그림 끝까지 무작정 가져다 쓰면 옆 구역 — 예: 엘리베이터
벽 — 을 잘못 가져오게 된다), 모자라면 고유 소품이 없는 조각 하나를 정해 그 폭만큼만 반복 타일링한다.
